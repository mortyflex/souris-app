# BeautIzzy — Project Instructions

## 1. Product

BeautIzzy is a lightweight native business and appointment management application for beauty professionals.

The first real-world implementation and validation context is:

- a hairdresser;
- a single professional;
- mobile-first daily usage.

However, BeautIzzy is NOT a hairdressing-only product.

The core domain must remain suitable for beauty professionals such as:

- hairdressers;
- nail technicians;
- estheticians;
- lash and brow professionals;
- other appointment-based beauty professionals.

The initial user experience may be optimized for hairdressing when this improves usability.

The core domain must not permanently couple BeautIzzy to hair salons.

Product principle:

> Generic in the data model, specific in the user experience.

Profession model: `docs/domain/PROFESSIONS.md`. A profession IS the stored `BusinessActivityType`;
`PROFESSIONS` / `isProfessionAvailable` decide what a NEW Business may choose (today
`HAIRDRESSING`, plus `NAILS`, `ESTHETICS` and `WELLNESS` opened to the pilot professionals). An
existing Business is never re-checked. Never infer that a profession is supported because its identifier or label exists.

---

## 2. Product Mission

BeautIzzy exists to give a beauty professional the minimum set of tools required to manage their daily business efficiently without the complexity of traditional salon-management software.

The application should feel:

- simple;
- fast;
- clear;
- native;
- warm;
- professional;
- pleasant to use repeatedly throughout the day.

BeautIzzy should not become an ERP.

BeautIzzy should not reproduce every capability found in large salon-management platforms.

Prefer a small number of excellent workflows over a large number of mediocre ones.

---

## 3. Product Simplicity

BeautIzzy competes on simplicity.

Do not add a capability merely because another salon-management application has it.

A new feature should normally answer at least one of these questions:

- Does it make appointments easier to manage?
- Does it make client follow-up genuinely useful?
- Does it make services and processing time easier to understand?
- Does it make product retail or stock easier to manage?
- Does it remove a repetitive daily task?
- Does it materially improve the professional's working day?

If not, it is probably outside the core product.

Do not introduce speculative product complexity.

# 11. Appointments Are the Core Domain

Appointments are the most important business concept in BeautIzzy.

Never simplify an appointment to:

```text
start + duration
```

A BeautIzzy appointment is composed of ordered service items.

Each item contains a snapshot of the service selected at the time of booking.

Each item contains ordered phases.

Conceptually:

```text
Appointment
├── id
├── businessId
├── clientId
├── staffMemberId
├── startAt
├── status
└── items[]
    ├── AppointmentItem
    │   ├── serviceId
    │   ├── serviceOptionId?
    │   ├── order
    │   ├── serviceName
    │   ├── serviceType
    │   ├── price
    │   └── phases[]
    │       ├── name
    │       ├── durationMinutes
    │       └── requiresStaff
    └── ...
```

Exact implementation types will be introduced deliberately in the domain phase.

Do not invent them prematurely in UI code.

# 12. Service Types

The scheduling domain distinguishes:

```text
SERVICE
TECHNIQUE
```

## SERVICE

A SERVICE is a simple professional service.

Examples:

- haircut;
- blow-dry;
- simple treatment.

A SERVICE requires the professional during its duration.

A SERVICE does NOT contain processing / unattended time.

---

## TECHNIQUE

A TECHNIQUE may contain multiple ordered phases.

Example:

```text
Application
15 min
requiresStaff = true

Processing
35 min
requiresStaff = false
```

A TECHNIQUE may also follow:

```text
active
→ processing
→ active
```

A TECHNIQUE may contain:

- processing time;
- zero processing time;
- multiple active phases;
- multiple ordered phases.

Never hardcode:

```text
TECHNIQUE = application + processing
```

The real abstraction is:

```text
TECHNIQUE = ordered phases
```

---

# 13. Processing Time

Processing time is a core BeautIzzy concept.

A phase where:

```text
requiresStaff = false
```

means:

- the client is still in the appointment;
- the appointment is still running;
- the professional is not required during that phase.

This may allow the professional to work with another client.

Examples include beauty workflows where a product, treatment, color, or other process must remain in place for some time.

Do not couple processing time specifically to hair coloring.

The concept must remain generic enough for other beauty professions.

---

# 14. Appointment Timeline

Appointment items are ordered.

Appointment phases are ordered.

The appointment timeline is calculated from:

```text
appointment start
+
ordered items
+
ordered phases
```

Reordering service items recalculates the timeline.

The timeline must be calculated by domain logic rather than visual components.

UI components consume the calculated timeline.

They must not independently invent timing rules.

---

# 15. Appointment Snapshots

Appointments must preserve historical reality.

When a service is added to an appointment, the appointment must eventually preserve the relevant service information as a snapshot.

If the catalog later changes:

- service name;
- price;
- duration;
- phases;

an existing historical appointment must not silently change.

Catalog configuration and appointment history are different concerns.

# 16. Appointment Overlap

Multiple appointments at the same time are allowed.

This is an explicit product rule.

The professional may intentionally handle multiple clients simultaneously.

Therefore:

- appointment creation must not automatically fail because another appointment overlaps;
- appointment movement must not automatically fail because another appointment overlaps.

Overlap detection may later support:

- information;
- warnings;
- suggestions;
- availability calculations;
- multi-staff capabilities.

But overlap is currently NON-BLOCKING for professional scheduling.

Do not reintroduce conflict blocking without an explicit product decision.

## Calendar Blocks — the one explicit exception

Personal unavailability is implemented as a dedicated entity, `CalendarBlock`.

Reference: `docs/domain/CALENDAR_BLOCKS.md`.

```text
CalendarBlock
├── id
├── businessId
├── staffMemberId
├── startAt
├── endAt
└── reason
```

It always reads « Indisponible » in the product.

It is calendar availability only.

It is NOT an Appointment variant.

Never give it, and never model it as:

- a fake client;
- a zero-price service or a fake appointment item;
- a price, a discount or a payment;
- an Appointment status.

It lives in its own table, its own session and its own sync aggregate (`CALENDAR_BLOCK`).

It never appears in the Cash Register, the Client profile, `Total dépensé`, the history or Sales.

That isolation is structural: financial and client derivations take Appointments and Sales.

Do not add a "skip blocks" filter to financial code; keep blocks out of those inputs.

The explicit product decision (September 2026):

- a Calendar Block may not overlap another Calendar Block of the same staff member;
- a Calendar Block may not overlap a STAFF-REQUIRED interval of an Appointment of the same staff member;
- a client Appointment may not be created or moved into a Calendar Block of its staff member;
- that holds for EVERY change of an Appointment, the quick edits of Appointment Details included;
- a change whose staff-required intervals are identical is never checked;
- adjacent intervals are fine: ends are exclusive;
- processing time (`requiresStaff = false`) never conflicts;
- `CANCELLED` and `NO_SHOW` Appointments occupy nothing;
- another staff member's schedule is never looked at.

ONE domain rule decides: `findCalendarBlockConflict` / `findAppointmentCalendarBlockConflict`.

Every change of an existing Appointment goes through `findAppointmentChangeCalendarBlockConflict`.

Compute the candidate first; compare occupied intervals, never the start/end envelope.

Never duplicate the comparison in a screen.

Overlap between client Appointments stays NON-BLOCKING.

The reason is plain text.

The quick suggestions of the editor are a UX shortcut, never an enum.

The staff identifier of Appointments and Calendar Blocks comes from ONE source:

`src/features/appointments/current-staff-member.ts`.

Not implemented yet:

- recurring, all-day or multi-day blocks;
- working hours, breaks as settings, time off;
- an availability policy for online booking.

Do not build these before their dedicated phase.

# 17. Manual Scheduling vs Future Online Booking

Manual professional scheduling and future customer self-booking are different concerns.

They must not share one simplistic definition of availability.

## Manual professional scheduling

The professional controls their own agenda.

They may intentionally:

- overlap appointments;
- work with another client during processing time;
- accept unusual scheduling arrangements.

Overlaps are therefore non-blocking.

---

## Future customer self-booking

Future customers may eventually book appointments remotely.

BeautIzzy must then expose only appointment slots considered bookable under a dedicated availability policy.

Do NOT assume:

```text
"the professional is technically allowed to create this appointment"
```

means:

```text
"this slot should be offered to a customer online"
```

Future online-booking availability may consider:

- business working hours;
- staff working hours;
- breaks;
- time off;
- existing appointments;
- service phases;
- processing phases;
- configurable concurrency rules;
- booking lead time;
- booking horizon;
- blocked periods;
- service availability;
- staff availability.

These rules are FUTURE scope.

Online booking is an approved direction: its public pages live in `web/` (§5), and professional booking management stays in the Expo application.

Build each part of it — availability, booking creation, payments, database changes — only in the phase that explicitly requests it.

Do not build an online booking engine speculatively.

Design the domain so that an availability layer can be added later without rewriting the Appointment model.

# 21. Client Data: Implemented and Future Capabilities

## Implemented

Two optional pieces of BeautIzzy-created client information are stored on the client: birthday and notes.

They are persisted locally and synced (see §23).

The client profile also shows information DERIVED through `clientId`, never stored on the client.

Reference: `docs/domain/CLIENTS.md`.

### Birthday

```text
birthday?: { month, day }
```

- domain value: `{ month, day }`;
- persistence and sync key: civil `MM-DD` text;
- annual semantics: it recurs every year from day + month alone;
- a year is never required, asked for, stored, or invented;
- it is a calendar value, never an instant: never convert it through a `Date`, a timestamp, or UTC;
- client creation and editing support it, including clearing it;
- the client profile displays it;
- the client directory never displays it (see Client directory below).

### Notes

```text
notes?: string
```

- one optional free-text note per client;
- nullable: a blank note is no note (`undefined` in the domain, `NULL` in storage);
- trimmed at the edges, internal line breaks preserved;
- no categories and no medical model;
- never imported from legacy data (§20 still applies);
- client creation and editing support Notes;
- the client profile displays Notes when present;
- notes never appear in the client directory and are not searchable.

### Client directory

Reference: `docs/design/DESIGN_OVERRIDES.md` §36.

```text
[ rounded-square photo / initials ]  Client name                 >
```

Client Directory rows:

- use the same directory grid as the Products list;
- use the 52pt rounded-square `ClientAvatar`: the client photo when available, two initials otherwise;
- end with the shared navigation chevron; the whole row is the one action;
- use the shared 72pt minimum row height;
- use the same subtle row separators as Products;
- do NOT display birthday dates or the `Aujourd'hui` badge.

The birthday lives on the client profile and in the appointment flows.

Do not restore it in directory rows.

### Appointment history (derived)

The client profile lists the client's BeautIzzy appointments: `appointment.clientId === client.id`.

- grouped as upcoming (`À venir`) and history (`Historique`), plus the next appointment when one exists;
- cancelled and no-show appointments stay in the history;
- only permanent appointment deletion removes a row;
- legacy visits are never imported (§20 still applies).

### Spending and activity (derived)

The profile `Activité` section shows:

- completed appointments;
- total spent;
- no-shows;
- cancellations made by the client.

Total spent (`Total dépensé`) is everything the identified client spent, over the whole BeautIzzy history.

ONE domain rule decides: `src/domain/clients/spending.ts` (`getClientTotalSpentCents`).

It includes:

- the value of `COMPLETED` appointments: services net of each appointment's discount (`docs/domain/APPOINTMENTS.md` §15.3);
- the products sold during those appointments (« Revente »), counted once, through the appointment;
- paid standalone product sales attributed to the client (`clientId`, no `appointmentId`, a recorded `payment`).

It never includes:

- a non-completed, cancelled or no-show appointment, nor the products sold during it;
- a sale without a client;
- a standalone sale without a recorded payment (historical); no payment is ever invented for it;
- a deposit as extra spending: it is a way of paying the appointment.

It never uses current catalog prices.

Tops & tendances « Clients qui dépensent le plus » reads the SAME rule, scoped to its period.

The two amounts may differ only because of that time scope.

Never reimplement client spending in a screen or in Insights.

The section stays visible at zero.

None of these values is stored on the client.

### Purchases (derived)

The profile `Achats` section (formerly `Produits achetés`) lists the client's sales: `sale.clientId === client.id`.

Its counter counts purchases — Sales, one per transaction — never product units.

A multi-product Sale stays ONE row.

It reads sale item snapshots, so later product edits or deletion do not change it.

Every purchase row — the profile preview and the complete history — opens the shared Sale Detail screen (`/sales/[saleId]`), the one the Cash Register opens.

The complete purchase history offers the existing swipe-revealed « Actions » and the shared `SaleActionsSheet`, selected by `getSaleActions` exactly as in the Cash Register.

Refunds and corrections reuse the existing Sales domain (`docs/domain/SALES.md` §15): no separate workflow, no separate records.

A row's refund state reads the Sale refund summary (`describeSaleRefundStatus`); a voided entry never counts as a refund.

Reference: `docs/design/DESIGN_OVERRIDES.md` §48.4.

Nothing is stored on the client.

### Birthday experience

ONE domain rule decides: `isClientBirthdayOnDate(client, date)`.

`isClientBirthdayToday` delegates to it.

Never duplicate the comparison in a screen.

The compared date depends on the context:

- client profile: TODAY's local date;
- appointment creation, editing and Details: the APPOINTMENT date.

A `29 février` birthday is celebrated on the 28th in a year without a 29th.

Implemented:

- profile: a `Joyeux anniversaire` reminder card;
- profile: one short confetti burst and one haptic on EVERY profile entry (per mount), never on a rerender;
- Reduce Motion: no confetti, the card stays;
- appointment creation, client step: selecting a client whose birthday is the appointment date shows a compact reminder at once, with the same burst and one haptic per explicit selection;
- the copy says `aujourd'hui` only when the appointment date is today, `ce jour-là` otherwise;
- appointment creation and editing: a birthday reminder next to `Réduction`;
- `Appliquer une réduction` only opens the existing generic discount editor;
- appointment Details: a static birthday mention.

The birthday never discounts anything by itself.

Nothing is preselected.

No discount origin, reason or birthday flag is stored.

No celebration state is persisted or kept in a session.

Archived clients are never celebrated.

### Not implemented yet

- automatic birthday discounts;
- birthday discount source or history;
- advance birthday reminders and notifications;
- marketing automation;
- cash register changes tied to a birthday.

Do not build these before their dedicated phase.

## Future

Client information created by BeautIzzy may later include:

- technical formulas;
- before/after photos;

These are future features.

Do not introduce them before their dedicated phases.

# 23. Persistence

Persistence is implemented.

- local: SQLite (`src/persistence`), forward-only migrations — `docs/architecture/PERSISTENCE.md`;
- cloud: Supabase, through the existing aggregate sync — `docs/architecture/CLOUD_SYNC.md`.

SQLite is the operational database.

The cloud is a synced copy of it.

Client data currently persisted and synced through the `CLIENT` aggregate:

- identity and contact fields;
- `archived_at`;
- `birthday` — `MM-DD` text, nullable;
- `notes` — free text, nullable.

Client notes are persisted locally (SQLite schema v9, `clients.notes`).

Client notes are synced through the existing aggregate sync.

There is no separate sync mechanism for them.

Calendar Blocks are persisted locally (SQLite schema v11, `calendar_blocks`).

They are synced through the existing aggregate sync as their own aggregate type, `CALENDAR_BLOCK`.

Schema v11 also rebuilds `sync_outbox` and `sync_state`.

SQLite cannot alter a CHECK, and their `aggregate_type` vocabulary is CHECKed.

Every row, id and the AUTOINCREMENT sequence are carried over.

Appointment deposits are persisted locally (SQLite schema v12, `appointment_deposits`).

They are synced through the existing aggregate sync as their own aggregate type, `APPOINTMENT_DEPOSIT`.

Schema v12 rebuilds `sync_outbox` and `sync_state` with the same procedure as v11.

Service categories and the two optional Service fields (`category_id`, `description`) are persisted locally (SQLite schema v17, `service_categories`).

They are synced through the existing aggregate sync as their own aggregate type, `SERVICE_CATEGORY`, and two optional SERVICE keys (`docs/architecture/CLOUD_SYNC.md` §27).

Schema v17 rebuilds `sync_outbox` and `sync_state` with the same procedure as v11.

Sale adjustments — corrections and refunds of completed Sales — are persisted locally (SQLite schema v18, `sale_adjustments` + `sale_adjustment_items`).

They are synced through the existing aggregate sync as their own aggregate type, `SALE_ADJUSTMENT` (`docs/architecture/CLOUD_SYNC.md` §28). A completed Sale is never rewritten: see `docs/domain/SALES.md` §15.

Schema v18 rebuilds `sync_outbox` and `sync_state` with the same procedure as v11.

v11, v12, v17 and v18 are the only non-`ALTER` migrations of the project.

Sync is per aggregate.

A build that predates an aggregate type never names it, so it can never delete it.

Real client data exists.

Every schema change, local or remote, must be:

- additive;
- nullable;
- backward compatible;
- non-destructive;
- a normal forward migration.

Never edit an applied migration.

Never wipe, reset, or reseed a database to change its schema.

Supabase migrations are applied by hand.

Never apply them automatically.

Do not add:

- another persistence technology;
- AsyncStorage persistence;
- new database abstractions;
- a second sync engine;

before explicitly requested.

The domain must remain independent from the persistence technology.

(and `.dev`), the SQLite file `souris.db`, the `souris_metadata` table, the
`SOURIS_EMAIL_LOGO_URL` secret, the `souris-communication-…` idempotency key, applied
migrations, and internal `Souris*` TypeScript identifiers such as `SourisDatabase`.

Do not copy design reference images into runtime assets unless they are actually needed by the application.

Design references and application assets are different concerns.

---

# 28. Testing

Business-critical domain rules require automated tests.

Appointment scheduling is especially important.

Tests should cover behavior rather than implementation details.

Important appointment rules to test progressively include:

- service type behavior;
- ordered phases;
- `requiresStaff`;
- processing time;
- timeline calculation;
- multi-item appointment ordering;
- timeline recalculation after reorder;
- overlapping appointments allowed;
- lifecycle behavior;
- historical snapshots.

Do not delete tests merely because implementation changed.

If a product rule intentionally changes, update tests explicitly.

---

# 29. Validation

The project should eventually expose:

```bash
npm run check
```

as the normal validation command.

Once configured, it should validate the relevant project quality gates such as:

- tests;
- lint;
- TypeScript.

Use:

```bash
npm run check
```

for normal final validation.

Run targeted tests separately only when diagnosing a real failure.

Do not repeatedly run multiple redundant validation commands without reason.

---

# 30. Real Device Validation

Automated tests do not replace real mobile testing.

When a phase changes important interaction behavior, include a manual real-device checklist.

Examples:

- gestures;
- long press;
- drag;
- keyboard;
- camera;
- barcode scanner;
- bottom sheets;
- navigation;
- safe areas.

Never claim that real-device validation was performed unless it actually was.

---

# 31. Accessibility

Native interfaces should be accessible by default.

Pay attention to:

- meaningful accessibility labels;
- sufficient contrast;
- readable text sizes;
- touch targets;
- focus where relevant;
- information not communicated only by color;
- reduced motion when appropriate.

Do not add accessibility complexity unrelated to the current feature, but do not create obvious barriers.

---

# 32. Code Style

Prefer:

- strict TypeScript;
- descriptive names;
- small files with clear responsibilities;
- explicit data transformations;
- immutable domain operations where practical;
- pure functions for business logic.

Avoid:

- `any` without justification;
- hidden side effects;
- unnecessary mutation;
- clever abstractions;
- deeply generic APIs;
- duplicated business rules.

Keep UI logic and business logic separated.

---

# 33. Scope Discipline

Every implementation task has a defined phase.

Implement ONLY the requested phase.

Do NOT:

- start the next roadmap item;
- refactor unrelated modules;
- install speculative dependencies;
- build future infrastructure;
- redesign unrelated UI;
- clean the whole repository because you noticed something unrelated.

If an unrelated issue is discovered, mention it in the final summary under `Points to review`.

Do not fix it unless it blocks the requested work.

---

# 34. Agent Skills

Project-installed skills may provide useful implementation guidance.

They are subordinate to:

1. current user/task instructions;
2. this `CLAUDE.md`;
3. project documentation;
4. existing architecture.

Do not introduce architecture, dependencies, abstractions, or design changes merely because a skill recommends them.

BeautIzzy project conventions take precedence.

# 35. Git

Use Conventional Commits with an emoji.

Examples:

```text
chore: 🚀 initialize BeautIzzy native
docs: 📚 define BeautIzzy agent guidelines
feat(appointments): 📅 add appointment timeline
test(appointments): 🧪 cover processing phases
fix(appointments): ↔️ allow overlapping appointments

```

Agents must NOT commit or push unless explicitly instructed.

Normal agent implementation tasks end before commit.

---

# 36. Agent Behavior

Before implementing:

1. read `CLAUDE.md`;
2. read `AGENTS.md`;
3. inspect the live repository;
4. read relevant project documentation;
5. inspect relevant tests;
6. identify the smallest necessary implementation.

When implementation is requested:

Do not stop after inspection.

Do not return only a plan.

Do not ask for confirmation unless blocked by a genuinely destructive or ambiguous decision.

Complete the requested implementation.

Run the required validation.

Then immediately return the requested final summary.

Do not wait for another user message before returning the summary.

Do not commit.

Do not push.

---

# 37. Definition of Done

A phase is complete only when:

- requested behavior is implemented;
- business rules remain correct;
- architecture boundaries are respected;
- relevant tests exist;
- required validation passes;
- no unrelated feature was started;
- real-device validation steps are documented when relevant;
- the agent has returned a concise implementation summary.

Correctness and simplicity are preferred over feature quantity.
